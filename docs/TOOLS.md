# Tools

The authoritative tool contract is `schemas/tools.json`, exported from the
running server (§33.1) via `dev-workspace-mcp export-schemas`. This file is
a human-readable index alongside it — per §72, generated by hand rather
than by a script for now (no task in `docs/TODO.md` builds a generator);
if the two disagree, `schemas/tools.json` is right and this file is stale.
CI (`.github/workflows/ci.yml`) fails if a tool this file lists diverges
from `schemas/tools.json`'s own tool names, so "stale" here means "not yet
regenerated locally," not "silently drifted since the last release."

Current tool surface — `docs/SPEC.md` §34.1 lists the fixed MVP set this
implements in full; Post-MVP Operations adds explicitly versioned operator
tools beyond that original set (24 tools total as of O12):

| `server_info` | Server version, capabilities, and health (§25, PMOR-004, PMOR-005, PMOR-011). O10 adds a read-only `operations` summary alongside the existing audit and maintenance sections. It reports bounded inventory completeness, state-filesystem capacity/free space and pressure, and cgroup-v2 PID usage/limit and pressure. State-filesystem free space at or below 10% and bounded PID utilization at or above 90% are reported as `pressured`; optional probe failure is explicit `degraded`/`unavailable` with `None` metric values rather than fabricated zero. ## Operations

| Tool | Purpose |
| --- | --- |
| `resource_inventory` | Bounded, read-only inventory of MCP-owned operational resources, cleanup debt, degraded/unavailable observations, and optional Linux PID pressure (PMOR-001..005, PMOR-010). Durable cleanup debt includes both retained job-log cleanup and O9 SSH-agent post-primary cleanup; pending debt remains byte-accounted until absence is proven. PID pressure trusts only cgroup v2: `/proc/self/cgroup` selects the daemon cgroup and `pids.current`/`pids.max` under `/sys/fs/cgroup` provide usage/limit; unavailable sources are explicit and never become zero. Optional repository/workspace filters are opaque IDs only; no host path filter is accepted. |
| `resource_prune_plan` | Dry-run-only immutable reclamation planning (PMOR-006..007, PMOR-010, PMOR-012). Accepts only optional opaque repository/workspace scope plus an optional subset of the five supported reclaimable kinds, including durable `ssh_agent_cleanup` debt; it has no execute/confirmation/path/generic-Docker input. Returns an immutable `pp_…` plan token, positively owned candidate IDs/kinds/reasons/preconditions/actions, and projected bytes while preserving unavailable byte values. Planning performs no stop/kill/remove/prune action; raw SSH boot/process-start and cleanup device/inode identity remain plan-internal, while the public preconditions report only whether cleanup identity is bound. Plan creation emits path-safe audit metadata containing the plan ID plus opaque candidate IDs/kinds, bounded reasons, and `planned` decisions. |
| `resource_prune_execute` | Explicit plan-scoped reclamation execution (PMOR-008..010, PMOR-012). Accepts only an existing immutable `pp_…` plan token plus `confirm` (default `false`); omitted/false confirmation performs no resource inspection or mutation. With explicit confirmation, each exact planned identity is independently revalidated immediately before its candidate-specific action. The executor never recomputes/expands the plan and has no label-wide, prefix-wide, path-wide, or system-prune fallback. Per-candidate results distinguish reclaimed, already-proven-absent, stale, and failed/unprovable identities; public `reason` values are restricted to allowlisted failure classifications and arbitrary free-form failure detail becomes `failure_detail_redacted`. Aggregate status distinguishes `success`, `mixed`, and `degraded` (or `not_confirmed`). If SSH-agent primary reclamation succeeds but socket cleanup fails, the primary failure context is preserved as a failed candidate while path-free durable cleanup debt remains discoverable, byte-accounted, and safely retryable by the original plan or a fresh cleanup-debt plan. Execution audit metadata records only the plan ID, confirmation/aggregate state, opaque candidate IDs/kinds, decisions/outcomes, reclaimed bytes where known, and allowlisted/sanitized failure classifications; arbitrary host paths, secrets, Docker credentials, SSH key material, and raw environment values are not copied into audit output. |

### Automatic maintenance boundary

Lifecycle maintenance may retry cleanup debt that existing lifecycle semantics have already authorized, including GAP3 Y7 job-log cleanup debt and O9 exact-identity SSH-agent secondary-cleanup debt. It does not create or execute a `resource_prune_plan` merely because inventory reports an old, stopped, retained, visible, or pressured resource.

Automatic age- or pressure-based resource reclamation is not implemented. Any future policy that automatically reclaims healthy retained caches, stopped-but-retained workspaces, or images requires a separate explicit configuration contract, conservative defaults, and its own acceptance criteria before it may cross the destructive boundary.

## Structured Git (§17, §20)

Host-side reads (§20.1) and in-container mutating operations, run through
the same execution service `exec` uses.

| Tool | Purpose |
| --- | --- |
| `git_status` | Structured repository status: branch, head, ahead/behind, staged/unstaged/untracked (§17.2). |
| `git_diff` | Working-tree, staged, or commit-to-commit diff; path-filtered, stat-only mode, byte-range pagination (§17.3). |
| `git_log` | Bounded commit history (§17.3). |
| `git_commit` | Create a commit from explicit paths, with branch/HEAD guards and policy checks (§17.4, §20.6, §45, §18.9). |
| `git_pull` | Fetch then integrate from a validated remote, per `git_policy.pull_strategy` (§20.5, §18.8). |
| `git_push` | Push to a validated remote with a daemon-constructed refspec — never a client-supplied one (§20.3, §20.5, §18.9). |

`schemas/tools.json`'s own `contract_version` field is the authoritative
current value (bumped per §33.2's rules whenever the tool surface or an
output shape changes; see `src/dev_workspace_mcp/schema_export.py`'s own
change-comment history for what each bump was) — not repeated here, so
this file does not itself go stale on every patch bump the way an inlined
number would.
