### The new feature: job promotion on overrun

- `exec` accepts a new optional input, **`promote_on_timeout`** (default `false`).
- **Without it**, nothing changed: a command that outlives the synchronous timeout
  (`execution.sync_timeout_seconds`, default 30 s) is killed and the call fails with
  `COMMAND_TIMEOUT`.
- **With it**, the command is *not* killed. It carries on as a background job, the same
  process never restarted, and `exec` returns a job handle:
  - `promoted_to_job: true`
  - `job_id`, `state` and `started_at`
  - every completed-result field (`exit_code`, `stdout_tail`, …) is `null`
- The job is then followed with `exec_status`, `exec_output` and `exec_cancel`, like any
  `exec_start` job. Output produced before promotion is at the start of the job's log.
- The job's timeout (`execution.default_job_timeout_seconds`, default 3600 s) counts from
  when the command started, not from promotion.
- Every `exec` response now carries `promoted_to_job` (`false` for a completed command).

**The output schema.** It is one flat object whose top-level `properties` also carry a
two-branch `oneOf`, discriminated on `promoted_to_job`. Two alternative shapes were probed
against the real MCP SDK and rejected (JPO spec §2.5). It has been validated with the
Python MCP SDK and `jsonschema`, **but never with ChatGPT** — hence the smoke check below.

## 3. The manual ChatGPT smoke check

### 3.1 Purpose

Confirm ChatGPT's connector accepts `exec`'s new output schema and reads both response
shapes correctly: completed, and promoted to a job. Nothing else in the project needs you.

### 3.2 Prerequisites on the laptop

1. **Linux, Docker running, `uv`, Python 3.12** (see `README.md` → Development
   environment).
2. **Get the code:**
   ```bash
   git clone git@github.com:ekkus93/mcp-chatgpt-sandbox.git   # or: git pull on an existing clone
   cd mcp-chatgpt-sandbox
   uv sync --group dev
   git config core.hooksPath .githooks
   ```
3. **Build the default workspace image**, if the laptop does not have it:
   ```bash
   docker build -t mcp-chatgpt-sandbox-ubuntu:24.04 docker/default/
   ```
4. **Configure the server and the ChatGPT tunnel.** The wizard handles both:
   ```bash
   uv run mcp-chatgpt-sandbox setup
   uv run mcp-chatgpt-sandbox doctor --config ~/.config/mcp-chatgpt-sandbox/config.yml
   ```
   Use a disposable or test repository. For the tunnel (`tunnel-client`, profile, tunnel
   ID), follow `docs/CONNECTING_CHATGPT.md`. It has a wizard path and a manual path.
5. **Optional, recommended:** set a short synchronous timeout so the overrun test is quick,
   in `~/.config/mcp-chatgpt-sandbox/config.yml`:
   ```yaml
   execution:
     sync_timeout_seconds: 5
   ```
   With the default of 30 s, just make the test command sleep longer (60 s works).

### 3.3 Start the server and refresh ChatGPT

1. Start the server (via the tunnel profile, or directly for a local client):
   ```bash
   uv run mcp-chatgpt-sandbox serve --config ~/.config/mcp-chatgpt-sandbox/config.yml
   tunnel-client run --profile <your-profile>
   ```
2. **Refresh / rescan the ChatGPT app.** The `exec` tool's schema and description changed,
   so ChatGPT must re-read them (`docs/CONNECTING_CHATGPT.md` → "Refreshing tool
   metadata").
3. While rescanning, confirm the `exec` tool now lists a `promote_on_timeout` input.
4. Start a new conversation with the app enabled.

### 3.4 The checks

Record the date, the server's commit (`git rev-parse --short HEAD`), and, for any failure,
the exact error text ChatGPT shows.

| # | Ask ChatGPT to… | Expected |
|---|---|---|
| 1 | Open a workspace for your test repository (`workspace_open`). | A running workspace and a `workspace_id`. |
| 2 | Run `echo hello; echo oops >&2; exit 3` with `exec` (no promotion). | The call is **accepted** (no schema or validation error). ChatGPT reports exit code **3**, stdout `hello`, stderr `oops`. `promoted_to_job` is `false`. |
| 3 | Run `echo start; sleep 20; echo done` with `exec` and **`promote_on_timeout: true`** (use `sleep 60` if you kept the 30 s default). | The call **returns** after the synchronous timeout, not after the whole command. It is accepted, with `promoted_to_job: true`, a `job_id`, and `state: "running"`. ChatGPT does not complain about `exit_code` being null. |
| 4 | Check that job with `exec_status` until it finishes. | It reaches `succeeded` with exit code `0`. |
| 5 | Read its stdout with `exec_output`. | Contains `start` then `done`: output from before and after promotion, in order. |
| 6 | *(Optional)* Run `sleep 300` with `promote_on_timeout: true`, then `exec_cancel` the job. | `exec_status` reaches `canceled`. |
| 7 | *(Control)* Run `sleep 20` with `exec` and **without** the flag (with the 5 s timeout). | Fails with `COMMAND_TIMEOUT`, exactly as before the feature. |

### 3.5 Recording the result

- **All pass:** tick both boxes under each of PJPO-006, PJPO2-004 and PJPO3-004 (§2.1).
  Add a short evidence note to each: date, server SHA, the two checks' results. Update the
  three TODOs' Status lines from "Complete except …" to "Complete". Commit directly to
  `master` with a `docs:` subject.
- **Anything fails:** don't work around it. Record what happened under the task, leave the
  boxes unticked, and open a new finding. If ChatGPT rejects or mis-reads the schema, the
  documented fallback is JPO decision D2's option B (a flat nullable object *without* the
  `oneOf`). That trades away SPEC §14.4's "express the union explicitly" and needs a
  `contract_version` bump, so it is a decision, not a quick fix.

## 4. Working notes for the laptop

- **Conventions** (`CLAUDE.md`): work traces to a task ID in a spec+TODO pair; commit
  directly to `master` with conventional-commit subjects; always run the full suite; no
  `Co-Authored-By` lines in commit messages. The desktop has a global `commit-msg` hook
  enforcing that last rule; the laptop may not, so it is on you there.
- **Pre-commit hook** (`.githooks`, enabled by `git config core.hooksPath .githooks`) runs
  `ruff format --check`, `ruff check` and `mypy src`. `ruff format` also formats Python code
  blocks inside Markdown files, so a docs commit can be blocked by a snippet. Run
  `uv run ruff format <file>` and re-commit; don't bypass the hook.
- **Tests need Docker and the test image:**
  ```bash
  docker build -t mcp-chatgpt-sandbox-test-s7:24.04 docker/default/
  uv run pytest
  ```
  Any skip counts as a failure (`tests/_skip_policy.py`), so an unreachable Docker daemon
  fails the run rather than skipping. Some tests use `/dev/full` and are Linux-only by
  design.
- **CI runs on a self-hosted runner on the desktop machine.** Pushes from the laptop get CI
  only while that runner is online. Otherwise they sit queued until it comes back.
- **On the desktop**, the Claude Code background-task memory guard killed long background
  `pytest` runs, so full suites were run in the foreground in four chunks (non-workspace,
  then `tests/workspace/test_[a-f]*`, `[g-o]*`, `[p-z]*`). On a laptop without that
  constraint, a plain `uv run pytest` is fine.
